# EZLove 易挂念项目立项及生产落地方案

> 版本：1.0  
> 日期：2026-08-11  
> 部署边界：阿里云中国内地，最多 1 台弹性云服务器  
> 目标：以单社区政府试点为第一阶段，在 8-12 周内完成可审核、可试运行、可运维的生产版本

## A. 立项背景

EZLove 不是从“还能给老人装什么设备”出发，而是来自三个反复出现的真实家庭处境：异地子女很久才知道老人住院或离世；老人发生意外时，子女因为工作无法及时发现；家人彼此关心，却因为报喜不报忧、联系频率低和“不知道说什么”，让信息在家庭里延迟流动。

LoveToken 公益 AI 挑战赛让团队把这种个人经验转化成了一个可验证的产品命题：**能否不安装摄像头、不要求老人佩戴设备，也不改变老人的日常习惯，仅通过家人关心、微信阅读、社区食堂和邻里探访等自然互动，获得足够温和的状态信号？**

比赛中的一个关键验证来自老照片。团队将家人的黑白结婚照修复并生成动态视频，老人看到后主动在家庭群里回应。这个反馈说明，AI 的价值不是替代家人说话，而是创造一个愿意开口、愿意回应的共同话题。项目获得最佳解法奖，并得到真实社区推进落地的意向。因此本次立项的目标不是继续打磨比赛 Demo，而是在一个真实社区内验证这条“牵挂驱动的无感守护”路径是否成立。

## B. 用户问题

### B.1 异地子女：关心存在，但联系成本很高

- 工作和距离导致联系不规律，家庭又习惯报喜不报忧。
- 打电话常常重复固定话题，久而久之更难主动开口。
- 真正焦虑的不是看不到实时数据，而是异常发生后很久才知道。
- 用户需要的是一个低负担的日常联系入口，以及在信号中断时被温和提醒。

### B.2 老人：需要的是原来的日常，不是患者身份

- 摄像头、持续定位和穿戴设备会强化“被监控、被照护”的感受。
- 多数老人已经会使用微信收消息和发语音，不愿再学习复杂应用。
- 老人希望看到家人的生活、社区的饭菜和熟悉的照片，并以最简单的方式回应。
- 产品应在老人原有生活中工作，而不是要求老人为了守护系统改变生活。

### B.3 社区工作人员：需要减少排查，不是增加一套系统

- 老旧社区通常无法稳定获得水、电、门禁等外部数据。
- 工作人员覆盖老人数量多，信息主要来自电话、走访、食堂和邻里反馈。
- 新系统如果要求维护大量表单，会把“数据完整”转化为基层负担。
- 社区端只应保留看板、邻里帮任务和菜单推送三类核心工作，零散信息由结构化 Agent 辅助整理。

## C. 产品命题

**一句话定位：** EZLove 是一个以家人牵挂为入口、以自然互动为状态信号、以社区协作为兜底的独居老人关怀平台。

**核心机制：**

```text
家人问候 / 社区菜单 / 邻里任务
                 ↓
服务号把通知送入微信会话，老人点击查看、回应或线下参与
                 ↓
系统形成“已读、回应、食堂、探访”多来源状态信号
                 ↓
正常：不打扰     信号中断：提醒家属     持续未确认：社区人工核实
```

“已读就是在线”不是安全结论。它只是低成本、低侵入的弱信号。系统不得把一次未读直接描述为危险，也不得把一次已读描述为绝对安全；多个信号中断后，仍由家属或社区工作人员人工确认。

## D. 用户价值与设计原则

1. **牵挂优先于监控。** 用户首先感知到的是家人分享和社区服务，不是状态采集。
2. **提醒而不是告警。** 面向家属使用“今天好像还没看手机，打个电话？”；只有社区内部处置流程才使用风险事件等级。
3. **AI 负责打开话题，不替人表达感情。** 所有发给老人的 AI 内容必须由家属确认或编辑后发送。
4. **不增加老人操作负担。** 老人端围绕微信消息、单列大字页面、大按钮、语音和表情回应设计。
5. **不增加基层表单负担。** 能从业务行为自动形成的数据不重复录入；Agent 输出结构化结论，不做泛聊天入口。
6. **允许解释正常缺席。** 旅游、住院、回子女家等期间可设置状态说明和有效期，避免误判。
7. **技术永远是辅助信号。** 本产品不提供医疗诊断、生命体征监测或紧急救援承诺。

## E. 首期用户与范围

### E.1 试点对象

- 一个真实社区，首批 50-100 位老人，稳定后扩至 100-500 位。
- 优先纳入会使用微信收消息的独居/空巢老人及其至少一名家属。
- 对没有智能手机或不会独立操作的老人，不排除在关怀体系之外，由邻里帮任务、护工、食堂和社区走访补充人工信号。
- 社区工作人员控制在一个站点或网格团队内，先跑通责任链再扩社区。

### E.2 P0 核心闭环

1. 家属与老人建立绑定关系。
2. 家属发送文字、图片或经确认的 AI 问候，服务号在获批模板和触发规则内通知老人。
3. 社区按实际运营节奏发送食堂菜单，为老人提供真实服务价值；是否可按日触达以服务号消息能力审核结果为准。
4. 老人查看内容或做简单回应，系统记录阅读信号。
5. 超过家庭设置的时间仍未读，家属收到温和提醒并电话确认。
6. 家属无法确认时，可发起社区协助；工作人员通过电话、走访或邻里帮完成核实并留痕。
7. 老人外出或住院时，家属/社区设置状态说明，暂停不必要提醒。

### E.3 P1 情感内容

- 老照片修复、上色和动态视频，用于创造家庭共同话题。
- 文生音频，把家属确认后的文字或社区菜单转换为可播放的普通话/方言友好语音。
- 文生音频使用明确的系统音色，不默认模仿子女或逝者声音；声音复刻必须单独取得被复刻者明确授权，并默认不进入首期范围。
- AI 生成的音频和视频在家属创作端标识来源，并由家属确认；老人端不伪装成真人实时发送。

## F. 三类核心用户旅程

### F.1 家属：从“想起才联系”到“每天有一个开口理由”

首页看到老人近期状态和推荐话题，选择照片、日常文字或 AI 建议，编辑确认后发送。老人阅读后，家属看到“已查看”；若超过阈值未查看，只收到一条克制的联系提醒。目标不是提升消息数量，而是让有效联系更稳定。

### F.2 老人：收到有用或有情感价值的内容

老人从服务号会话、服务通知或家庭群中的小程序卡片进入大字页面，看到家人的照片、问候、修复后的老照片，或社区当天菜单。无需主动寻找小程序、注册新账号、理解风险分或维护状态；看完可以用一个表情、语音或“我看到了”回应。

### F.3 社区：只处理需要人工判断的少数情况

工作人员先看整体活跃趋势，再查看持续缺少信号且没有外出说明的老人。Agent 汇总来自已读、食堂、探访和历史事件的结构化信息；工作人员决定电话、任务分发或走访，并对结果负责。

## G. 立项目标与衡量指标

### G.1 北极星指标

**每周形成至少一次有效双向关怀互动的试点老人占比。**

有效互动包括：老人查看家属/社区内容并回应、家属根据提醒完成电话确认、食堂参与被记录、邻里探访完成并确认。单纯后台打开页面不计入。

### G.2 试点成功指标

| 维度 | 8 周试运行目标 | 说明 |
|---|---:|---|
| 激活 | >= 70% 的受邀家庭完成绑定 | 验证 onboarding 是否可用 |
| 有效互动 | >= 60% 的活跃老人每周至少 1 次双向互动 | 验证情感价值 |
| 阅读信号 | >= 70% 的推送在 24 小时内被查看 | 只作行为指标，不等于安全率 |
| 家属行动 | >= 50% 的持续未读提醒在 12 小时内被确认处理 | 验证提醒是否有效 |
| 社区减负 | 需要人工核实的老人数量相较全量日排查下降 >= 30% | 需用试点前基线对照 |
| 误扰 | 因外出/住院等已知情况产生的无效提醒 < 10% | 验证状态说明机制 |
| 老人体验 | >= 80% 的受访老人认为“不麻烦、没有被监控感” | 访谈或简短问卷 |
| 系统质量 | 核心流程成功率 >= 99%，无跨家庭/社区数据泄露 | 技术红线 |

### G.3 立项阶段不承诺的结果

- 不承诺通过已读信号发现所有意外。
- 不把已读率包装为老人安全率或健康指标。
- 不替代 120、社区应急值班、医疗服务和家属照护责任。
- 不把 AI 生成量、Agent 对话数或安装量作为项目成功的主要指标。

## H. 试点运营方案

### H.1 招募与启动

- 由社区筛选首批老人并完成知情沟通，家属自愿加入。
- 采用线下说明会 + 一对一绑定，不要求老人自行完成复杂注册。
- 为每位老人确定一名主要家属和一个社区责任网格，明确谁接提醒、谁做升级处置。
- 首周只开启家庭消息和菜单，不开启风险提醒；观察真实阅读习惯后再设置个人阈值。

### H.2 日常运营

- 菜单按社区真实节奏推送，不能为了采集信号制造无价值消息。
- 家属每周至少发送一次真实内容，AI 只提供建议和创作素材。
- 社区每天固定时间查看待确认列表，不要求全天盯看板。
- 邻里帮任务包含接单、完成、老人确认/工作人员复核和积分发放，避免任务只停留在分发。

### H.3 异常升级

```text
超过个性化阈值未读
  -> 提醒主要家属
  -> 家属标记“已联系正常”或“暂时无法确认”
  -> 无法确认且满足社区规则时，提交社区协助
  -> 社区电话/邻里任务/走访
  -> 人工记录结果并关闭事件
```

任何自动化只能到“建议下一步”和“创建待办”，不能自动判断老人发生危险或自动派发紧急救援。

### I.4 立项闸门

- **G0 允许建设：** 发起人、社区、预算、主体、试点范围和负责人明确。
- **G1 允许导入测试数据：** 隐私清单、测试协议、账号权限和删除流程通过评审。
- **G2 允许真实用户试点：** 微信审核、备案、生产安全、备份恢复和运营手册通过验收。
- **G3 允许扩大到 500 人：** 50-100 人运行满 4 周，未发生重大隐私事件，误扰率和社区工作量可接受。
- **G4 决定长期运行：** 完成 8 周指标与访谈复盘，明确持续预算、运维主体和年度目标。

项目必须保留停止条件：发生跨家庭数据泄露、未经授权发送敏感数据到 AI、连续严重误报导致社区无法承受、老人明显产生被监控感且无法通过产品调整解决时，立即暂停扩面并复盘。

## 1. 决策摘要

采用“单台 ECS 承载计算与数据库，阿里云 OSS 承载媒体，境内合规 API 承载 AI”的方案。

- ECS 内运行：Nginx、FastAPI、PostgreSQL 16、Redis 7、管理后台、定时任务和备份任务。
- OSS 存放：用户原始图片、生成图片、生成视频、海报和数据库加密备份。
- AI 采用可插拔的境内 API：文本和 Agent 首选阿里云百炼；文生音频、文生/图生视频可选火山引擎豆包语音与火山方舟，也可按政府采购结果切换其他合规供应商。
- 微信端使用一个小程序承载子女、老人和志愿者角色，并增加一个认证服务号作为老人主要触达入口。政府项目方负责提供合法主体、认证账号、域名、备案资料、隐私文本和类目资质。
- 服务号与小程序绑定到同一微信开放平台账号，通过 UnionID 打通身份。老人从微信服务号会话/服务通知进入内容页，不需要主动寻找小程序。
- 政府 App 通过独立的政务数据交换接口获取经授权、按用途裁剪的数据，不直接连接 EZLove 数据库。
- 首期只使用 1 个备案主域名和 2 个业务子域名：`api.<主域名>`、`admin.<主域名>`。可选增加 `static.<主域名>` 绑定 OSS，自定义域名总数最多 3 个。
- 不采用 Supabase 托管版，也不在 ECS 自托管完整 Supabase。现有 PostgreSQL + SQLAlchemy 架构直接上线，降低跨境、资源和运维风险。

本方案不是高可用架构。单机故障时业务会中断，因此把自动备份、监控告警和 4 小时内恢复作为强制验收项。

## 2. 项目方必须解决的前置条件

以下事项由政府项目方或其指定运营公司完成，技术承建方提供材料模板和配置协助，但不能代替主体承担责任。

| 类别 | 项目方交付物 | 阻塞范围 |
|---|---|---|
| 主体 | 政府/事业单位/公司主体及经办人授权 | 小程序注册、认证、备案、云账号 |
| 微信小程序 | 已认证账号、AppID、AppSecret、管理员与体验成员 | 微信登录、订阅消息、审核发布 |
| 微信服务号 | 已认证服务号、AppID、AppSecret、消息模板/类目权限、服务器配置 | 老人微信会话触达、菜单与关怀通知 |
| 微信开放平台 | 将服务号和小程序绑定到同一开放平台账号 | UnionID 身份打通 |
| 小程序类目 | 与社区养老、生活服务实际业务匹配的类目及所需资质 | 提审与发布 |
| 域名 | 完成实名认证且主体一致的可备案域名 | HTTPS API、管理后台、小程序合法域名 |
| 备案 | ICP 备案；上线后按要求完成公安联网备案；是否需要 App 备案由项目方和接入商确认 | 中国内地公网访问 |
| 隐私合规 | 隐私政策、用户协议、个人信息处理规则、第三方 SDK 清单、撤回/注销渠道 | 小程序审核、正式运营 |
| 数据授权 | 老人、家属、社区工作者数据来源与授权边界，尤其是手机号、地址、健康备注和告警记录 | 数据导入与生产试点 |
| 内容与 AI | AI 服务使用规则、生成内容标识规则、人工审核责任人、禁用场景 | AI 功能开放 |
| 微信消息 | 订阅消息模板 ID 及实际模板字段 | 未读提醒和告警通知 |
| 政府 App 对接 | 接口规范、网络区、安全认证、数据目录、联调联系人和验收环境 | 数据回传与政府 App 内展示 |

阿里云明确要求中国内地服务器上的互联网服务完成 ICP 备案；网站开通后还应在规定时间内完成公安联网备案。备案资料、时长和前置审批以主体所在省通信管理局及阿里云控制台当期要求为准。

### 3.1 ECS 规格

推荐生产规格：

- 8 vCPU、16 GiB RAM，Alibaba Cloud Linux 3 或 Ubuntu 22.04 LTS。
- 系统盘 ESSD 100 GiB；独立 ESSD 数据盘 200 GiB，挂载 PostgreSQL 数据目录。
- 固定公网 IP 或 EIP，公网带宽 5-10 Mbps 起步。
- 安全组仅开放 22、80、443；22 只允许运维固定 IP，数据库和 Redis 不映射到公网。
- Docker Engine + Compose v2；所有镜像固定版本，不使用 `latest`。

最低可运行规格为 4 vCPU、8 GiB，但不建议同时开启 AI 媒体任务轮询、报表导出和批量导入。若只能购买 4C8G，FastAPI 限制为 2 个 worker，PostgreSQL `shared_buffers` 设为 1 GiB，并限制 AI 并发为文本 5、图片 2、视频 1。

### 3.2 容器与资源上限

| 服务 | 建议内存上限 | 说明 |
|---|---:|---|
| PostgreSQL | 4 GiB | 数据持久化到独立数据盘 |
| FastAPI | 3 GiB | 2-4 workers，健康检查与优雅重启 |
| Redis | 512 MiB | 开启密码和 AOF，`maxmemory-policy allkeys-lru` |
| Nginx + 管理后台 | 512 MiB | TLS、静态文件、反向代理 |
| 监控/日志代理 | 1 GiB | 可使用阿里云云监控插件或轻量代理 |
| 系统余量 | 7 GiB | 文件处理、备份、突发任务 |

### 3.3 数据库选择

正式方案使用本机 PostgreSQL 16。

- 现有代码已经使用 SQLAlchemy 2.0 async、asyncpg 和 Alembic，无需迁移 ORM。
- Supabase 托管版没有中国大陆托管区域，不作为政府项目默认数据底座。
- 自托管完整 Supabase 官方建议 4 核 8GB 以上，还会增加 Kong、Auth、Realtime、Storage、Studio 等容器；本项目已有认证、API 和存储层，引入后收益小、单机风险高。
- 若未来允许增加托管资源，优先迁移阿里云 RDS PostgreSQL，而不是改写为 Supabase。

## 4. 域名、证书和网络

### 4.1 域名数量

必需：1 个备案主域名，2 个子域名。

| 域名 | 用途 | 微信后台配置 |
|---|---|---|
| `api.example.cn` | FastAPI、上传、SSE Agent | request 合法域名、uploadFile 合法域名、downloadFile 合法域名 |
| `admin.example.cn` | 社区管理后台 | 不需要配置到小程序 |
| `static.example.cn`（可选） | OSS 图片/视频自定义域名 | downloadFile 合法域名；如客户端直传则加入 uploadFile |

表中的 `example.cn` 是部署占位符，实施时必须整体替换为项目方完成实名认证和备案的真实主域名。

不需要为数据库、Redis、百炼、微信 API 单独购买域名。它们分别通过 Docker 内网或供应商域名访问。

### 4.2 HTTPS 与安全组

- 使用阿里云数字证书管理服务或受信任 CA 证书，覆盖 `api`、`admin`，可使用通配符证书。
- 强制 HTTPS，TLS 1.2+；80 仅做 301 跳转。
- Nginx 设置上传大小、超时、SSE 不缓存；AI 视频提交接口快速返回任务 ID，禁止保持数分钟 HTTP 长连接。
- PostgreSQL 5432、Redis 6379、FastAPI 容器端口只在 Docker 网络开放，删除当前 Compose 中的公网端口映射。
- 后台管理端增加 IP 白名单或 VPN 是推荐项；至少开启 MFA、强密码、登录失败锁定和操作审计。

## 5. 微信服务号、小程序与用户信息

### 5.1 主体责任边界

代码不能绕过主体和用户授权。项目方需要在微信公众平台完成主体认证，技术方只接入主体提供的 AppID/AppSecret。未取得主体、类目和隐私审核前，只能发布体验版，不能承诺正式上线。

### 5.2 获取信息的正确方式

| 信息 | 获取方式 | 是否静默 | 本项目用途 |
|---|---|:---:|---|
| `openid`、`session_key` | 小程序 `wx.login` 获取 code，后端调用 `jscode2session` | 是 | 建立账号和登录态 |
| 昵称 | 用户主动输入，或经授权后获取微信提供的能力 | 否 | 家庭展示、社区档案 |
| 头像 | 用户主动选择头像或上传 | 否 | 展示，可首期不收集 |
| 手机号 | 用户点击带 `getPhoneNumber` 能力的按钮，后端用动态 code 换取 | 否 | 告警联系、社区工作；非核心流程不得强制 |
| 地址/健康备注 | 社区工作人员在有业务授权的情况下录入 | 否 | 关怀服务；属于高敏感业务字段 |
| 图片/视频 | 用户主动选择并上传 | 否 | 发送牵挂、AI 生成输入 |
| 订阅消息授权 | 每次在明确业务场景调用 `requestSubscribeMessage` | 否 | 未读提醒、告警通知 |

现有代码只完成了 `wx.login -> jscode2session -> openid -> JWT`。没有发现手机号授权接入；昵称与角色目前依赖用户后续填写。正式上线前必须新增手机号动态 code 的后端换取流程，或明确首期完全不采集手机号。

### 5.3 最小必要原则

- 首次进入只获取 `openid`，不强制昵称、头像和手机号。
- 用户进入“绑定老人”“接收电话告警”等确需手机号的功能时，再解释目的并请求授权。
- 老人端默认不展示风险分、健康备注或社区内部标签；家属端只展示其绑定关系内的数据。
- AI 请求不得默认发送手机号、完整地址、身份证号、健康备注等直接标识信息。Agent 工具返回给 LLM 前使用内部 ID，并按角色裁剪字段。
- 提供账号注销、关系解绑、数据导出/更正、撤回授权和删除上传媒体的入口。
- 隐私政策列明微信、阿里云、OSS、百炼和短信服务等第三方处理者以及数据用途、范围、保存期限和联系方式。

### 5.4 服务号触达方案

服务号的定位是“把有价值的通知送到老人已经会使用的微信会话里”，小程序负责展示具体内容和采集阅读信号。老人仍需点击服务号消息或小程序卡片才能查看内容，但不需要主动打开微信下拉栏、搜索小程序或学习新的入口。

#### 账号与身份打通

1. 项目方申请并认证一个与小程序同主体的微信服务号。
2. 服务号和小程序绑定到同一微信开放平台账号。
3. 老人线下扫码关注服务号；工作人员或家属协助完成一次性绑定。
4. 服务号侧保存 `official_openid`，小程序侧保存 `mini_openid`，后端通过同一 `unionid` 关联到一个 EZLove 用户；任何无法确认的身份不得自动合并。
5. 取消关注、绑定冲突和 UnionID 缺失时保留人工核验流程。

#### 消息类型与产品用途

| 消息能力 | 适用内容 | 限制与处理 |
|---|---|---|
| 服务号模板/服务通知 | 家人新关怀、当天菜单、待确认提醒等明确服务事件 | 用户必须关注；模板和字段需微信审核；不得做营销或无业务事件群发 |
| 客服消息 | 老人主动互动后的答复、人工帮助、小程序卡片 | 只在微信规定的互动时效窗口内使用，不能作为稳定的每日主动推送通道 |
| 服务号菜单 | “今天菜单”“家人消息”“联系社区” | 用户主动进入服务号后的固定入口 |
| 小程序订阅消息 | 家属侧未读提醒、任务处理通知 | 每次按微信规则获取用户授权，作为服务号之外的补充通道 |
| 家庭微信群分享 | 家属主动分享小程序卡片 | 最接近真实家庭沟通，但系统不能强制或自动替家属发送 |

服务号消息出现在服务号会话或微信服务通知中，**不等同于家属个人微信聊天消息**。能否按日发送菜单、能否使用“小程序卡片”样式、模板字段和发送频率，都要以项目主体在微信公众平台实际获批的能力为准。

#### P0 验证要求

- 在 20 位体验用户中完成服务号关注、UnionID 绑定、消息送达、点击进入小程序和已读回传全链路测试。
- 分别统计送达率、点击率、24 小时阅读率、取消关注率和老人完成任务所需步骤。
- 若模板无法覆盖“家庭关怀/社区菜单”场景，不通过营销话术规避审核；改用家属分享、小程序订阅消息、服务号菜单或降低推送频率。
- 微信回调接口使用独立路径 `/api/v1/wechat/official/callback`，校验签名、时间戳和重放；AppSecret、Token、EncodingAESKey 不进入前端。
- 新增服务号消息审计：业务事件、模板 ID、接收用户、发送时间、微信 `msgid`、结果码、点击/阅读回传，不保存完整消息正文到普通访问日志。

## 6. AI 方案

### 6.1 多供应商、统一适配层

AI 能力不与单一供应商绑定。后端按 `text`、`vision`、`image`、`audio`、`video` 五类能力定义内部 Provider 接口，业务层只创建任务，不直接拼接供应商 URL。默认组合为：

- 文本、视觉理解、Agent：阿里云百炼华北 2（北京）。
- 文生音频：火山引擎豆包语音中国大陆服务。
- 老照片修复：百炼万相图像编辑，或经过效果和采购验证的其他境内图像 API。
- 文生/图生视频：火山方舟视频生成 API；百炼万相视频作为可切换备选。
- 内容审核：阿里云内容安全或火山引擎内容安全，采购时统一选定一个主服务。

百炼提供 OpenAI 兼容接口，现有 `AsyncOpenAI` 封装可通过修改 `LLM_BASE_URL`、`LLM_API_KEY` 和 `LLM_MODEL` 接入。音频和视频必须经过独立 Provider，不能继续用一个 `VIDEO_GEN_API_KEY` 代表所有供应商。

推荐环境变量：

```dotenv
LLM_PROVIDER=aliyun_bailian
LLM_API_KEY=<DASHSCOPE_API_KEY>
LLM_BASE_URL=https://<WorkspaceId>.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
LLM_MODEL=qwen-plus
BAILIAN_WORKSPACE_ID=<WorkspaceId>
BAILIAN_API_BASE=https://<WorkspaceId>.cn-beijing.maas.aliyuncs.com/api/v1
TTS_PROVIDER=volcengine
VOLCENGINE_TTS_APP_ID=<AppId>
VOLCENGINE_TTS_ACCESS_TOKEN=<AccessToken-or-AKSK>
VIDEO_PROVIDER=volcengine_ark
VOLCENGINE_ARK_API_KEY=<ARK_API_KEY>
VOLCENGINE_VIDEO_MODEL=<控制台已开通的视频模型Endpoint或ModelId>
OSS_BUCKET=<private-bucket>
OSS_ENDPOINT=oss-cn-beijing.aliyuncs.com
```

模型 ID 和 Endpoint 会随平台更新。生产发布时在供应商控制台锁定已验证版本，不自动追随 `latest`；文档中的模型名只代表候选模型族。每次更换模型必须回归测试老人肖像真实性、内容安全、中文表达、生成时延和成本。

### 6.2 AI 功能与具体 API

| 功能 | 首选模型/服务 | API | 当前代码状态 | 上线级别 |
|---|---|---|---|---|
| 暖心文案建议 | `qwen-plus` | `POST .../compatible-mode/v1/chat/completions` | 已实现，需配置并强化 JSON 解析 | P0 |
| 食堂文本解析 | `qwen-plus` | 同上，要求 JSON Schema/结构化输出 | 已实现 LLM 解析链路 | P0 |
| 图片理解与配文 | 支持视觉输入的千问 VL 模型，以控制台可用型号为准 | OpenAI 兼容 Chat Completions，多模态消息 | 已实现 base64 图片输入，但默认 `qwen-plus` 未必支持视觉，必须拆分模型配置 | P0 |
| 社区 Agent | `qwen-plus` 或工具调用验证更稳定的千问型号 | OpenAI 兼容 Chat Completions `tools`/function calling | 已实现 7 个工具和最多 5 轮调用 | P0 只读；写工具 P1 |
| 老照片增强 | `wan2.7-image` 或万相通用图像编辑 | `POST .../api/v1/services/aigc/multimodal-generation/generation`；旧编辑接口为异步任务 | 只有 503 占位代码 | P1 |
| 文生音频 | 火山引擎豆包语音 TTS | 豆包语音在线合成 API；短文本返回 MP3/OPUS，长文本使用异步合成 | 未实现 | P1 |
| 文生/图生视频 | 火山方舟视频生成模型；百炼 `wan2.7-i2v` 备选 | 火山方舟视频生成任务 API；百炼备选为 `POST .../video-synthesis` + `GET .../tasks/{task_id}` | 只有 503 占位代码 | P1 |
| AI 生成内容审核 | 阿里云内容安全服务，或项目方指定审核服务 | 文本/图片/视频检测 API | 未接入 | P0 文本和上传图片；P1 视频 |

### 6.3 文本生成链路

1. 小程序调用 `POST /api/v1/ai/suggest`。
2. 后端按用户角色、时间和可选上下文构造提示词；不得拼入无关个人信息。
3. 调用百炼 OpenAI 兼容 `chat/completions`，请求超时 15 秒，最多重试 1 次。
4. 使用 JSON Schema 或 Pydantic 校验输出，拒绝任意非结构化 JSON；当前直接 `json.loads` 的实现需要加固。
5. 经过文本安全审核后返回 3 条建议。
6. 用户必须确认或编辑后才能发送；AI 不能自动代用户向老人发送消息。
7. 模型不可用时返回仓库内置文案，并记录 `fallback=true`。

### 6.4 图片与视频生成链路

1. 客户端向后端申请上传凭证，图片直传私有 OSS；首期也可经 API 上传，但最终必须转存 OSS。
2. 后端创建 `ai_media_tasks` 记录，保存用户、输入对象 key、模型、状态、积分预扣和幂等键。
3. 调用百炼异步生成 API，保存供应商 `task_id` 后立即返回 `202 Accepted`。
4. 单机定时任务每 5-10 秒轮询，使用 Redis 锁防止重复处理；禁止使用常驻 Celery 集群。
5. 成功后在结果 URL 失效前下载并转存私有 OSS，执行内容审核并写入输出对象 key。
6. 客户端轮询本系统 `GET /api/v1/ai/media/tasks/{id}`，通过 10 分钟有效的 OSS 签名 URL 展示结果。
7. 失败、超时或审核拒绝时自动退还积分；同一幂等键不能重复扣费。

现有媒体接口缺少任务表、供应商调用、轮询、OSS 转存、内容审核和任务查询接口，不能仅填写 `VIDEO_GEN_API_KEY` 就上线。

### 6.5 文生音频链路

1. 家属先确认要发送的文字，或社区确认当天菜单内容。
2. 后端执行文本审核，并删除手机号、地址等不应被播报的信息。
3. 调用火山引擎豆包语音在线 TTS；短消息输出 MP3 或 OPUS，设置偏慢语速和清晰普通话音色。
4. 音频转存私有 OSS，数据库记录文本摘要、音色 ID、语速、供应商请求 ID 和生成来源。
5. 老人端同时展示原文和播放按钮，不自动播放；失败时仍可阅读原文。
6. 家属语音复刻、逝者声音复刻和“冒充真人实时语音”默认禁止。后续如立项，必须增加单独授权、撤回、样本删除和显著 AI 标识。

音频的产品目标是无障碍阅读和降低老人阅读负担，不是制造“家属亲自录音”的错觉。

### 6.6 Agent 的 LLM 与边界

当前 Agent 已实现这些工具：

- `query_inactive_elders`
- `get_building_summary`
- `get_elder_status`
- `get_today_alerts`
- `list_unconfirmed_elders`
- `confirm_elder_active`
- `get_weekly_trend`

正式上线的控制要求：

- P0 只开放 6 个只读工具。`confirm_elder_active` 会写入社区事件，必须改为“生成确认卡片 -> 工作人员二次确认 -> 后端写入”，不得由 LLM 一步执行。
- 每个工具继续强制绑定 `worker.community_id`，并增加 RBAC；LLM 传入的社区 ID、用户 ID 一律不可信。
- Agent 最多 5 轮工具调用、单次最多 20 秒、单用户每分钟最多 10 次、单日 token 配额可配置。
- 对话历史首期不长期保存；保留请求 ID、工作者 ID、工具名、参数摘要、结果条数、模型版本、token 和错误码 180 天用于审计。日志不记录完整手机号和健康备注。
- Agent 回答必须显示“AI 辅助，不作为安全确认或医疗判断”；所有风险结论来源于规则与实时业务数据，LLM 只负责查询编排和解释。
- 禁止 Agent 自动发订阅消息、短信、删除数据、修改老人等级或关闭告警。
- 首期不需要 RAG。只有项目方提供经过审批的制度文件后，再增加知识库；业务实时数据仍通过受控工具查询，不能向量化全量个人信息。

## 7. 政府 App 数据接口

### 7.1 对接原则

政府 App 不连接 PostgreSQL，不复用管理后台 JWT，也不直接调用内部社区 API。EZLove 在同一 FastAPI 服务内增加独立的 `/openapi/gov/v1` 接口域，代码、鉴权、限流、日志和数据模型与公众端隔离；仍部署在同一台 ECS，不增加服务器数量。

- 先由政府方提供数据目录、接口规范、网络接入方式和安全要求；本方案给出默认合同，最终以双方联调文档为准。
- 只回传政府 App 展示或业务协同所必需的数据。默认提供聚合数据和去标识化状态，不默认回传家庭消息正文、照片、视频、AI 对话、健康备注、详细地址和手机号。
- 政府 App 内展示老人姓名或联系方式时，必须有明确业务依据、岗位权限和访问审计；列表默认脱敏，进入处置页按权限解密。
- “未读”“最近活跃”必须标注为行为信号，不在接口字段中命名为 `safe`、`healthy` 或“安全状态”。
- 每次数据出境界以项目方批准的数据字段清单为准，接口新增字段必须重新评审，不能静默扩充。

### 7.2 默认开放接口

| 方法 | 路径 | 用途 | 默认数据范围 |
|---|---|---|---|
| `GET` | `/openapi/gov/v1/communities/{id}/overview` | 政府 App 社区概览 | 老人数、今日有信号人数、待确认数、已处理数、趋势 |
| `GET` | `/openapi/gov/v1/communities/{id}/elders/status` | 分页获取老人状态 | 政府侧业务 ID、脱敏姓名、护理等级、最近信号时间/来源、状态说明、待确认标记 |
| `GET` | `/openapi/gov/v1/events` | 增量获取待确认和处置事件 | 事件 ID、类型、级别、创建时间、状态、责任网格；不含家庭消息正文 |
| `GET` | `/openapi/gov/v1/events/{id}` | 政府 App 事件详情 | 经授权的老人基础信息、信号时间线、处置记录 |
| `POST` | `/openapi/gov/v1/events/{id}/acknowledge` | 政府 App 接单/确认 | 政府操作人、部门、时间、备注、幂等键 |
| `POST` | `/openapi/gov/v1/events/{id}/resolve` | 回写处置结果 | 结果代码、处置方式、说明、完成时间、附件引用 |
| `GET` | `/openapi/gov/v1/metrics/daily` | 日报/大屏 | 按日聚合，不含个人明细 |
| `POST` | `/openapi/gov/v1/webhooks/subscriptions` | 登记政府回调地址 | 仅管理员配置，需双向验证 |

所有列表接口使用 `updated_since + cursor + limit` 增量分页，响应包含 `request_id`、`data_version` 和 `next_cursor`。写接口要求 `Idempotency-Key`，重复请求返回第一次结果，避免重复处置。

### 7.3 推送与拉取模式

- **P0 推荐政府 App 拉取：** 政府系统按 1-5 分钟增量拉取，架构简单，单 ECS 更容易控制失败重试。
- **P1 可选事件推送：** EZLove 在新建/升级/关闭事件时投递 webhook。事件进入本地 outbox 表，异步重试，政府端返回 2xx 才确认；连续失败转人工告警。
- webhook 只携带事件 ID、类型、时间和版本，政府 App 再按权限拉取详情，避免敏感数据滞留在消息队列或第三方网关日志。

### 7.4 鉴权与网络安全

优先级从高到低：政务外网/专网接入要求 > 政府统一 API 网关规范 > 本方案默认值。默认采用：

1. HTTPS TLS 1.2+，政府固定出口 IP 白名单。
2. OAuth 2.0 Client Credentials 获取短期 access token；如政府平台不支持 OAuth，则使用 `app_id + timestamp + nonce + body_sha256 + HMAC-SHA256` 签名。
3. 生产环境推荐双向 TLS（mTLS），客户端证书与 `client_id` 一一绑定。
4. scope 至少拆分为 `overview:read`、`elder_status:read`、`event:read`、`event:write`，不同政府应用单独授权。
5. 单客户端每分钟限流、请求体 1 MiB 上限、5 分钟时间偏差、nonce 防重放、敏感响应禁止 CDN/代理缓存。
6. 审计保存调用方、scope、接口、对象 ID、字段级数据集版本、响应码和 request ID；普通日志不保存完整响应体。

### 7.5 主数据与身份映射

- 政府系统和 EZLove 各自保留内部主键，通过 `external_id_mappings` 表维护 `system_code + external_object_type + external_id + ezlove_id`。
- 不用身份证号或手机号作为跨系统主键；首次导入由政府方提供稳定业务 ID。
- 冲突、重复和删除采用人工对账队列；接口删除默认是停用/撤回共享，不物理删除审计记录。
- 明确主数据归属：老人基础档案以政府指定系统为准，EZLove 负责家庭关系、自然互动信号和本系统处置过程。双向可写字段必须逐项指定唯一责任方。

### 7.6 对接验收

- 政府方先提供 OpenAPI/Swagger、字段字典、错误码、测试账号、白名单和联调环境。
- 使用虚构数据完成契约测试、分页/幂等/重放测试、权限越权测试和 1 万条增量同步压测。
- 断网 2 小时后恢复，不能丢事件或重复关闭事件；双方以 request ID 对账。
- 政府 App 页面必须显示数据更新时间、信号来源和“非医疗/非绝对安全判断”说明。
- 正式传输居民数据前，由项目方签署接口字段清单、保存期限、使用人员范围和安全责任确认单。

## 9. 现有代码上线缺口

### P0：不完成不能生产试点

2. OSS：替换本地 `static/uploads` 和 `static/ai_media` 长期存储，数据库只存 object key，不存永久公网 URL。

4. AI：拆分 `TEXT_MODEL`、`VISION_MODEL`、`AGENT_MODEL`；统一超时、重试、结构化输出、成本与调用审计。
5. Agent：写操作二次确认、RBAC、字段脱敏、Redis 限流、输入长度和历史条数限制。

7. 数据：生产迁移演练、种子数据与真实数据隔离、备份恢复演练、数据保存和删除策略。
8. 监控：CPU、内存、磁盘、容器、PostgreSQL、HTTP 5xx、任务积压、AI 失败率和证书到期告警。
9. 测试：微信真机主流程、老人端无障碍、权限隔离、告警定时任务、断网/超时/AI 降级、备份恢复。
10. 合规：用户协议、隐私政策、第三方清单、AI 标识与人工复核、账号注销和数据删除。
11. 修复已确认代码缺陷：`ai_media.py` 的视频生成端点引用未定义的 `point_service`；Redis 当前没有持久卷和密码；`/health` 只检查 `ANTHROPIC_API_KEY`，不能反映 `LLM_API_KEY`/百炼可用性。

## 10. 备份、恢复和运维

### 10.1 备份策略

- 每日 02:00 执行 `pg_dump --format=custom`，AES-256 加密后上传 OSS。
- 每周执行一次完整备份校验；每日备份保留 30 天，每月最后一份保留 12 个月，最终期限由项目方数据制度确认。
- OSS 开启版本控制、服务端加密和生命周期规则；备份账号只有写入指定前缀和读取恢复前缀的最小权限。
- 每月在隔离数据库执行一次恢复演练并记录 RTO/RPO。
- 目标 RPO 24 小时；目标 RTO 4 小时。若要求分钟级 RPO 或无停机，单 ECS 约束无法满足，必须增加 RDS/备机。

### 10.2 监控与告警

告警发送给至少两名运维人员：

- CPU > 85% 持续 10 分钟；内存 > 90%；数据盘 > 80%。
- API 5xx 比例 > 2% 持续 5 分钟；健康检查连续 3 次失败。
- PostgreSQL 连接使用率 > 80%；备份失败；证书 30 天内到期。
- AI 文本失败率 > 10%；视频任务超过 15 分钟；OSS 上传失败率 > 5%。

## 11. 分阶段实施计划

### 第 0 阶段：主体与云资源，预计 2-4 周，可与开发并行

- 项目方完成主体、阿里云账号、域名、ECS、OSS、百炼业务空间、小程序和服务号认证，并将两者绑定到同一微信开放平台账号。
- 提交 ICP 备案，准备小程序/服务号类目、消息模板与隐私材料；政府方提供 App 对接规范和联调环境。
- 决定手机号是否属于首期必要信息。

验收：小程序与服务号两套 AppID/AppSecret、开放平台账号、备案域名、ECS、OSS 私有桶、百炼北京 Key、消息模板申请单和政府接口联系人均有明确负责人。

### 第 1 阶段：生产底座，预计 1-2 周

- 完成生产 Compose、Nginx、HTTPS、安全组、环境密钥和 OSS。
- 完成数据库迁移、备份、监控和恢复演练。

验收：公网只开放 80/443/受限 22；数据库和 Redis 无公网端口；从 OSS 备份恢复到空库成功。

### 第 2 阶段：核心业务与微信，预计 2 周

- 接入正式微信登录、服务号回调与消息、UnionID 身份打通、订阅消息、合法域名和隐私声明。
- 完成家庭绑定、发送、查看、已读、告警和社区处理闭环。
- 完成角色越权与真机测试。

验收：至少 20 组模拟家庭连续运行 7 天；服务号消息完成送达、点击、小程序打开和已读回传；核心流程成功率 >= 99%，无跨家庭/跨社区数据泄露。

### 第 3 阶段：文本 AI 与 Agent，预计 1-2 周

- 接入百炼文本/视觉模型、结构化输出、内容审核、调用审计和降级。
- Agent P0 只读上线，写操作保留人工二次确认。

验收：200 条文案/解析测试结构化成功率 >= 98%；Agent 权限测试全部通过；供应商不可用时核心业务不受影响。

### 第 4 阶段：政府 App 联调，预计 1-2 周，可与第 3 阶段并行

- 双方确认数据目录、主数据责任、OpenAPI 合同、鉴权、白名单和错误码。
- 完成概览、老人状态、事件拉取与处置回写；如需要，再开启 webhook。
- 使用虚构数据执行契约、安全、幂等、断网恢复和 1 万条增量同步测试。

验收：政府 App 正确展示更新时间、信号来源和状态说明；双方可按 request ID 对账；越权 scope、重放请求和未授权字段均被拒绝。

### 第 5 阶段：试运行与审核，预计 2 周

- 50-100 名真实试点用户灰度，逐步扩到 100-500 名老人。
- 完成培训、值班表、故障预案、用户反馈和小程序提审。

验收：连续 14 天无 P0 故障；告警闭环可追溯；备份、恢复、注销和数据删除均演练通过。

### 第 6 阶段：AI 音频与媒体，预计 2-4 周，P1 可独立延期

- 接入火山引擎文生音频、老照片增强和文生/图生视频异步任务。
- 小流量灰度，设置每人/每日配额和总预算熔断。

验收：音频失败时保留文字阅读；媒体生成失败自动退款；结果完成后 5 分钟内转存 OSS；违规内容不下发；预算达到 80%/100% 时告警/停用。

## 12. 成本口径

具体价格受地域、购买时长、带宽、模型版本和采购折扣影响，正式采购前以阿里云控制台询价为准。预算表应分为：

- 固定成本：8C16G ECS、200GB ESSD 数据盘、固定公网带宽、域名、证书（可用免费证书但需管理续期）。
- 用量成本：OSS 存储/请求/外网流量、短信、百炼 token、图像张数、视频秒数、内容审核次数。
- 账号与集成成本：微信小程序/服务号认证、政府 API 网关或专网接入、联调测试环境。
- 人工成本：开发整改、备案材料、政府接口联调、测试、运维值班、内容审核和用户支持。

必须在后台配置三层 AI 预算：单用户日限额、单功能并发限额、项目月度金额上限。视频生成默认不开启，待项目方确认预算后灰度。

## 13. 上线验收红线

以下任一项不满足，不发布正式版：

- 主体、备案、类目、隐私政策或用户授权材料缺失。
- 数据库、Redis 或管理端调试接口暴露公网。
- 无成功的备份恢复演练，或备份与生产机在同一磁盘。
- 微信登录、家庭/社区权限存在越权漏洞。
- 服务号与小程序身份可能错误合并，或服务号消息能力未在真实主体下验证。
- 政府 App 可绕过 scope 获取未批准字段、可直接访问数据库，或接口操作无法审计对账。
- AI 可以未经用户确认自动发送内容，或 Agent 可以未经二次确认执行写操作。
- 用户上传和 AI 输出没有审核、举报和删除通道。
- 没有明确故障联系人、告警渠道和 4 小时恢复流程。

## 15. 最终责任分工

| 角色 | 负责内容 |
|---|---|
| 政府项目方 | 主体、预算、数据合法来源、业务制度、类目与前置资质、最终验收 |
| 运营主体 | 小程序/服务号认证与消息模板、隐私政策、用户服务、内容审核、投诉和注销处理 |
| 技术承建方 | 代码整改、部署、数据安全措施、AI 接入、测试、监控、备份和运维文档 |
| 阿里云 | ECS/OSS/百炼等云产品可用性及其责任边界内的安全能力 |
| 社区工作人员 | 老人档案授权录入、异常核实、Agent 写操作人工确认和处置留痕 |

项目上线负责人应维护一份带姓名、截止时间和证据链接的交付清单。主体问题由项目方解决，但未解决前必须在项目计划中标记为正式发布阻塞项。
